## 二、本曲设计（写进 `song.json`）

- **F 大调 / 67.6BPM / 67 小节 / 237.9s**，6 段：`intro(8) A1主歌(16) B1副歌(16) A2(8) B2副歌(12) OUT(7)`
- 和声按上面骨架走；副歌用 `C# / D#6/9` 做借用色彩
- 音色（gorgeous 基底 + 按指标改）：主奏 Synth Strings(51)、竖琴(46)、钢琴(0)、
  **Pad Sweep(95)**（连续高频层）、Synth Strings(51)、电贝斯(33)、钢片(9)、沙锤
- 旋律：**新写**，F 大调五声倾向、长音为主（慢歌 1~2 拍/音），强拍落弦内音

## 三、面板里的生产流程（这次实际点的按钮）

```
/api/new          脚手架（ref=amakute → 自动算出 rms -21.7 / width 1.89 / shelf 2.4）
写 song.json      作曲（数据层）
/api/check        数据契约 ✓
/api/song         保存（⚠ 这里发现并修了面板一个真 bug：`json_io` 不在子进程 sys.path → 保存失败）
/api/job render   = make_song --no-tune + finalize（宽度校准）—— **18 秒 / 238 秒的歌**
/api/metrics      绝对口径差表（面板指标栏）→ 驱动 v2…v7 共 6 轮改配比/音色（每轮 18s）
/api/job mixfit   解方程配平：实测 **3.47 → 1.91 dB**（第 2 遍变差 → 自动回滚）
/api/job search   候选搜索（副歌 8 小节切片）：39 次渲染 / 61.7s，切片 mad 3.21→2.56
/api/job export:stems  合并成品 + 9 条分轨
```

## 五、已知差距（诚实清单）

1. **10-18k 的连续性**：参考 占用 43.3%，本曲 8.7% —— GM 音源没有"既连续又到 18k"的非打击音色
   （见 `PITFALLS.md` 103 / `probe_timbre.py` 的实测表）。这条目前无法消除。
2. 低频两档仍偏薄（20-40 -2.9 / 40-80 -4.4）：参考曲是"薄底人声混音"，我们的编配偏器乐化。
3. **是器乐版**：人声旋律没有复刻（版权边界）；复刻的是语言与画像。
4. 面板 UX 两处待改（本次真实用到才暴露）：
   - 🧬 搜索的"采用"是**整包写回**（它把 `voicing_shift=-12`、`bass_style=offbeat` 也一起写进去了，
     实测反而变差 3.29 vs 1.91）→ 应支持**逐项采用/试听对比**。
   - 🎚 mixfit 的模型是线性的，遇到"编配缺能量"（如 5-10k 缺口）就无解 —— 到限幅时该提示"改音色/加层"。
