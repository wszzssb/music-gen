## 3. 已经否掉的（**别重复走**）

### 3.1 三个"看着像根因"的猜测，实测全否

| 猜测 | 实测读数 | 结论 |
|---|---|---|
| 引擎预设只有 5 种 ⇒ 伴奏织体/混音雷同 | 同预设 **0.132** vs 跨预设 **0.140**（差 **0.008**） | ❌ 不构成系统性差异 |
| 主题包和弦池重合 | 主题间 `harmony.primary` 的 Jaccard **平均 0.044**（只有 `neon↔retro` 1.00、`classic↔tender` 0.67 两对 ≥0.5） | ❌ 各主题分开 |
| 引子手法 `intro_style` 全局统一 | `new_song.intro_style_for()` 是 `crc32(曲名\|主题) % 候选数` ⇒ **按曲名随机** | ❌ 不是统一值 |

⚠ **特别提醒**：引子和弦**看着**很雷同（`C6` 出现在 9/17 首开头、`G7 C6 G7 C6` 与 `D7 G6`
各出现两次），但那是**同主题**的必然结果（`111`/`115` 都是 gorgeous、`106`/`116` 都是 classic），
**不是 bug**。查根因时先把它排除，别照"和弦雷同"去改。

### 3.2 两个改法**都破守卫**（`melody_form_rules` 的小节内最大空档门 ≤1.70 拍）

| 改法 | 结果 |
|---|---|
| 把 `_cell_fit` 的尾巴项改成"**达标即满分**"（`CELL_TAIL_W` 不再随格号增长） | 空档中位 1.38 → **1.75** ❌ 破门 |
| 在 C 组基础上再加"**含格 0 就给 +0.06**" | 空档 **1.81** ❌ 破门，且跨主题距离 0.202 → **0.161**（分化反而变小） |

**两条教训**（这是本文档最值钱的部分）：

1. **不能"取消"尾巴项、只能"减弱"** —— 末落点不再被推向靠后，小节内空档立刻变大。
   代码里原本就有一条同类警告（"首落点偏好靠前 `-0.015*min` → 末落点 ≥8 的小节 77%→61%"），
   本轮又踩了一次同族的坑。
2. **任何"单一强奖励项"都会让所有主题重新趋同** —— 加了格 0 奖励后排序又被格 0 主导，
   跨主题距离从 0.202 掉回 0.161。**要治某个格，只能让 `base` 本人对它敏感，不能另加主导项。**

## 4. 已实现的改动（C 组）——**已还原，但数据有效**

**改动只有一处**（`scripts/melody_gen.py`）：

```python
# 原：CELL_TAIL_W = 0.02
CELL_TAIL_W = 0.006   # 打分里"末落点越靠后越好"的权重（见 _cell_fit）
```

**为什么是这一处**：该项跨 8→14 格值 **0.16~0.28**，而画像重叠度 `base` 的差异常常只有
**0.05~0.1** ⇒ **尾巴项压过了画像**，于是所有主题都在追同一件事"把这一小节铺到后半"，
骨架自然收敛。

## 5. 下一步（⚠ **已被 §10 取代，保留作历史**）

> **2026-10-07 第二轮结论**：第 1 条（`_cell_fit` 的 `base`）**这一轮没动**，仍然有效但**不再是
> 第一优先级**（它治的是"落点偏低"，与"音色组合同质化"是两条线）；
> 第 2 条（"开头引出方式"）的**音色那一半已做完**（§10.2：引子 17/17 全是 GM4 → 13 种），
> **剩"各轨进入顺序/时间"没量**；
> 第 4 条（主奏撞色）**已证到顶**（§10.3 负结果 2：最大匹配上界就是 13/15）。
> **新的第一优先级 = §10.4 "骨架可变"**（`perc`/`pad` 服从 `arr_share`）。

1. **让 `base` 对"整格缺失"敏感**（治"格 0 偏低"与"骨架雷同"的共同上游）——
   把 `_cell_fit` 里的
   ```python
   base = sum(min(want.get(k, 0.0), w) for k, w in got.items())
   ```
   换成**分布相似度** `1 - 0.5 * sum(|want[k] - got[k]|)`（对"缺了画像高权重格"与
   "用了画像低权重格"**双向**惩罚，且**不引入新的主导项**）。
   ⚠ 换完 `base` 的取值范围会变（原 overlap ∈ [0, ~0.5]、新 ∈ [0.5, 1]）⇒ **必须同时重标
   `CELL_TAIL_W`**（否则尾巴项被稀释、空档又破门）。标定判据：`melody_form_rules` 的
   空档 ≤1.70 **且** 跨主题距离 **不低于 0.202**。
   ⚠ **不要**用"另加奖励项"的办法（§3.2 已证伪）。
2. **"开头引出方式"**（用户点名的第二项，本轮只摸到边）：本轮量到"引子的**编配开关组合**
   top 3 占 13/17 首"，但**没量过引子各轨的进入顺序/进入时间**（用户说的"引出方式"更像这个）。
   建议先量：每首引子前 2 小节里**各轨首个音的拍位**，看是不是"同一套进场顺序"。
   相关代码：`song_engine.shape_intro` / `shape_intro_add`（`arr.intro_style` 的消费方）·
   `new_song.intro_style_for`（写入方）。
3. `neon ↔ retro` 的 `harmony.primary` **一字不差**（Jaccard 1.00）—— 但两者的模板风格集
   本来就重叠（chiptune/game32 共有）⇒ 更像"**主题定义重叠**"而不是 bug，**要不要拆得用户定**。
4. 主奏两对撞色（`folk_tale`/`seaside` = GM87、`neon`/`tender` = GM80）—— 要动
   `new_song.lead_assign()` 的音色池。

  实验前**必须备份 `song.json` 并记 SHA256**（本轮就是这么还原的），改完核回 SHA256。
